## Context

The current exec Security page has 2 sections:
1. **Click-to-reveal risk explorer** (5 vuln cards + detail pane) — redundant with Summary's "Structural Risks to Address" list
2. **Hover-based DefenseDiagram** (4 layers) — good content, wrong format for exec scanning

The page needs a narrative arc that follows the pattern established on Summary and Scale & Extend: static, scannable, no interaction required, tells a story.

## Proposed Narrative Arc (5 beats)

### Beat 1 — "What Could Go Wrong"
Brief framing: the Summary named the risks, this page shows how the architecture closes each one. **Risk → Defense mapping table** — 4 rows, each risk from the Summary's "Structural Risks" list mapped to the specific defense layer that addresses it. Static table, same visual pattern as GovernanceInAction and Scaling Scenarios.

| Risk | Defense Layer | How It's Closed |
|------|-------------|-----------------|
| Data copies lose protection | Schema Inheritance | Tags cascade to every child object — copies in governed schemas inherit protection automatically |
| Enforcement depends on discipline | Tag-Based RAPs | RAPs bind to tags, not tables — no join to remember, enforcement fires at query time |
| Reshaping strips the rules | CI/CD Gate | dbt routing blocks promotion of misconfigured tables before they reach governed schemas |
| Onboarding takes tickets | ENTITLEMENTS (PDP) | Identity flows from Okta/Salesforce into ENTITLEMENTS — no manual grants |

### Beat 2 — "Defense in Depth" (static version)
Replace the hover-based DefenseDiagram with a static 4-layer vertical stack. Each layer gets a card with: layer number, name, one-line role, and what it blocks. Ordered outermost → innermost (CI/CD Gate → Schema Inheritance → Tag-Based RAPs → ENTITLEMENTS). Visual: numbered cards with a vertical "depth" indicator (border-left gradient from orange → green → blue → red), ending with "if all outer layers fail, ENTITLEMENTS still gates every query."

### Beat 3 — "Column-Level Protection"
Row-level security gets all the airtime. Masking is the other half. Brief section: Dynamic Data Masking operates *independently* of row filtering. PII columns are masked unless the querying user has an explicit unmask grant. Two controls, two dimensions: rows (who sees which records) + columns (who sees which fields). This fills the gap — the page currently says nothing about PII/masking.

### Beat 4 — "Compliance & Audit Posture"
What an exec expects on a security page: how does this map to compliance frameworks? Static table or card layout:
- **Auditability**: Single-table access ledger (ENTITLEMENTS) — point-in-time queries answer "who had access to what, when"
- **Least privilege**: Access derived from role, not granted manually — defaults to deny
- **Separation of duties**: Policy authorship (CI/CD + dbt) separated from enforcement (RAPs) separated from identity (Okta/SF)
- **Change traceability**: All policy changes flow through version-controlled dbt models

### Beat 5 — Closing callout
Similar to Scale & Extend's "The Bottom Line" — a green-accented callout: "Security isn't a layer bolted on after the fact. It's structural — built into how data moves, how identity resolves, and how policies propagate."

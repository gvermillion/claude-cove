## Context

The dashboard currently covers the **read path** — how RAPs enforce row-level access and how tags drive masking at query time. The user's side-chat describes a **write-path governance** model with three defense-in-depth layers that prevent misplaced data:

1. **RBAC gate** — ENTITLEMENTS → schema-level write grants (can't even `INSERT` without the right entitlement)
2. **Cortex Copilot** — semantic guardrail that inspects column patterns and validates data belongs in the target schema
3. **Stream + Task** — continuous post-write validation that flags missing/mismatched `DATA_DOMAIN` tags

## Implementation Steps

### Step 1 — Data model for write-path scenarios (~insert after masking data, before SECTION 2)

```ts
interface WriteScenario {
  role: string;
  entitlement: string | null;  // null = no entitlement
  targetSchema: string;
  tableName: string;
  domain: string;
}

interface WriteGateResult {
  rbac: { allowed: boolean; reason: string };
  copilot: { flag: 'pass' | 'warn' | 'block'; reason: string };
  validation: { status: 'ok' | 'flagged' | 'n/a'; reason: string };
}
```

Pre-built scenarios (3-4 roles × 2-3 target schemas):
- **HR analyst** writing to `HR__INDIVIDUAL` → RBAC ✓, Copilot ✓, Validation ✓
- **Sales analyst** writing to `HR__INDIVIDUAL` → RBAC ✗ (no HR entitlement), stops here
- **HR analyst** writing a sales-shaped table to `HR__BY_DEPARTMENT` → RBAC ✓, Copilot warns (columns look like sales data), Validation flags domain mismatch
- **New hire** writing to `SALES__GRANULAR` without tags → RBAC ✓, Copilot warns (no PII tags), Validation flags missing `DATA_DOMAIN`

A `resolveWriteScenario(scenario)` function computes the `WriteGateResult`.

### Step 3 — Write Path tab section (the main content)

**b) Defense-in-depth mini-pipeline** — three connected cards (similar to the enforcement lane visual):
```
RBAC Gate →(blocks)→ Copilot Guardrail →(validates)→ Stream + Task Validation
```
Each card shows: icon, title, one-line description, and a colored status indicator that reacts to the selected scenario.

**c) Write Scenario Simulator** — two-column layout:
- **Left:** Role selector (dropdown like RAP playground) + target schema selector (reuse schema list from Schema Design). Below that, a stacked card for each gate showing the result (✓/✗/⚠) with reason text and the relevant SQL/logic.
  - RBAC card: shows the `GRANT` check logic
  - Copilot card: shows the semantic inspection summary
  - Validation card: shows the stream+task SQL that would flag this scenario
- **Right:** "Write Decision" panel showing the final outcome — allowed, blocked at layer N, or allowed-with-warning. Similar to the "Resolved Outcome" panel in the tag playground.

**d) SQL blocks** for each layer (collapsible or stacked):
- RBAC: `GRANT INSERT ON SCHEMA HR__INDIVIDUAL TO ROLE hr_writer` + the sync proc pseudocode
- Copilot: semantic inspection prompt/output summary (not real SQL, but a structured description)
- Stream+Task: `CREATE STREAM` + `CREATE TASK` SQL with the validation query that joins `INFORMATION_SCHEMA.TABLES` against `TAG_REFERENCES`

**e) CalloutBox** — "ENTITLEMENTS → RBAC mapping" nuance (the new plumbing piece from the user's analysis: a stored proc or Task that syncs entitlement rows into Snowflake role grants).
